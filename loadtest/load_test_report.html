✅ 結論： 即使是最極端情境（全員 2 分鐘內回報），所需 RPS 約 83 req/s， 介於 200-user（60 RPS, 0% 失敗）與 500-user（137 RPS, 5.2% 失敗）之間。 搭配 Cloud Run 動態 Auto-scale（實測擴至 9–10 個 instance）， 系統在正常到中高壓力下均可零失敗運作。

測試結論

✅

表現良好

  • 零失敗率（50 & 200 users）：覆蓋所有真實情境，完全無錯誤
  • p50 延遲穩定：50ms → 52ms → 80ms，暖機後幾乎不隨人數增長
  • RPS 近線性擴展：15.7 → 59.9 → 137.3，顯示 Auto-scale 有效介入
  • GCP 實測 Auto-scale：500 users 時自動擴展至 9–10 個 instance
  • Pub/Sub 緩衝發揮作用：高峰寫入未造成資料庫直接壓垮
⚠️

可改善之處

  • Cold Start 尾延遲：200 users p95 從 320ms 跳至 1,600ms，新 instance 啟動慢
  • 500 users 5.2% 失敗：擴展期間請求 timeout，非程式邏輯錯誤
  • Dashboard 端點最慢：p95 在 500 users 達 5,200ms，需優化查詢或加 Cache
  • Token 共用限制：51 個帳號被 500 虛擬使用者共用，比實際情境更嚴苛
📊

數字解讀重點

  • p50 vs p95 的差距代表 Cold Start 影響，不代表穩定狀態差
  • 500 users 時 p95=2,300ms，但 p50 仍只有 80ms，表示大多數請求仍很快
  • 5.2% 失敗出現在最極端情境，且隨 instance 暖機後數字會改善
  • 實際用戶不會 0.5~3 秒就重發一次，真實壓力更低

優化建議

1

設定最小 Instance 數量 影響最大

目前 Cloud Run 從 0 instance 開始冷啟動，造成第一批請求 p95 劇升。設定 min-instances=2 可消除 Cold Start 問題。

gcloud run services update safety-response-api \ --min-instances=2 \ --region=asia-east1
2

Dashboard 加入 Redis Cache 影響最大

GET /dashboard/supervisor 在 500 users 時 p95 高達 5,200ms，是所有端點中最慢的。因為主管儀表板需要聚合大量資料，加入 5 分鐘 TTL 的 Redis Cache 可大幅降低 DB 壓力。

3

調整 Cloud Run Concurrency 設定 中等影響

目前預設每個 instance 允許 80 個並發請求。可根據實際測試調整此值，或配合 CPU 數量優化。

gcloud run services update safety-response-api \ --concurrency=40 \ --cpu=2 \ --region=asia-east1
4

Connection Pool 優化 中等影響

多個 Cloud Run instance 同時連接 PostgreSQL 可能耗盡連線數。建議加入 PgBouncer 或使用 Cloud SQL 的連線池模式，避免高峰時 DB 連線耗盡導致 5xx 錯誤。

5

增加真實帳號數量進行更準確的壓測 低影響

本次測試 51 個帳號被 500 個虛擬使用者共用，每個 token 被 ~10 個 user 同時使用，比真實情況更嚴苛。若測試帳號等於虛擬使用者數，失敗率預計會再降低。
